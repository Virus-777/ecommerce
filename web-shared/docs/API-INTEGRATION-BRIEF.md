**Working-tree note (uncommitted, not by this brief):** while this brief was written, `web-shared/vite.ts` gained a dev proxy (`/api`, `/graphql`, `/files` → `MARKETLY_API_URL`, default `http://127.0.0.1:4000`, `changeOrigin: false`) and a client appeared under `web-shared/src/api/` (`client.ts`, `session.ts`, `graphql.ts`, `errors.ts`, `openapi.d.ts`, `provider.tsx`). With the proxy, API calls are same-origin (`http://127.0.0.1:3000`), the refresh cookie lives on the app origin, and the backend still sees `Origin: http://127.0.0.1:3000` (allowed by the local `.env`). Reconcile §4.8 with that code.

**Use the same host name for the page and the API.** The refresh cookie is `SameSite=Strict`; `127.0.0.1:3000` → `127.0.0.1:4000` is same-site (ports don't count), but `localhost:3000` → `127.0.0.1:4000` is cross-site and the cookie would never be sent. Pick `http://127.0.0.1:4000` as `VITE_API_URL` (no proxy needed), or proxy `/api` and `/graphql` through Vite (then everything is same-origin).

**Secure cookie on plain http in development.** The backend has no dev override: the cookie is always `__Secure-mk_refresh_store=…; Path=/api/public/identity/sessions; HttpOnly; Secure; SameSite=Strict` (`backend/src/modules/identity/http/client.ts:39,56-63`; name and path `backend/src/kernel/auth/chain.ts:98-99`). Chromium (Chrome, Edge) and current Firefox treat `http://localhost` and `http://127.0.0.1` as potentially trustworthy origins and accept `Secure` / `__Secure-` cookies from them; Safari does not. Nothing in either repo exercises this in a real browser, so check it once in DevTools → Application → Cookies after the first `app-sessions` call. If it fails (Safari, or another host name): serve the API and the app over HTTPS locally (mkcert), or proxy through one HTTPS origin. Without a working cookie the app cannot refresh: a new app session means a new visitor session, which **loses the guest cart** after 15 minutes.

### 1.1 Token kinds the store holds

| Token | Lifetime | Claims (EdDSA JWT, `typ: at+jwt`, `iss: marketly-identity`) | Source |
|---|---|---|---|
| Visitor access token | 15 min (`accessTokenTtlMinutes`, 5–60) | `aud: store`, `kind: visitor`, `sid` = guest session id (cart, recently viewed, guest order grants hang off it), no `sub` | `docs/03-auth-middleware.md` §0, §5, §8 |
| Visitor refresh token | 30 days after last activity (`visitorRefreshDays`) | opaque `v.…`, hashed in `identity.guest_sessions` | `backend/src/modules/identity/service/registration.ts:27-47` |
| Customer access token | 15 min | `aud: store`, `kind: customer`, `sub` = account id, `sid`, `authAt`, `twoStepAt?` | `docs/api/modules/identity.md` Notes |
| Customer refresh token | 24 h (`refreshTtlHours`), 30 days with `keepSignedIn` (`keepSignedInDays`) | rotates on every refresh; reuse after the 20 s grace window revokes the session | `identity/service/core.ts:481`; `identity.md` Settings |

Keep the access token in memory only (never localStorage). The refresh token is never visible to JS on the website: responses that issue tokens to a `device.kind: "web"` caller return `refreshToken: ""` and set the cookie instead (`identity/service/core.ts:401-407`).

### 1.2 Which requests use `credentials: 'include'`

Only the routes that set, clear or read the refresh cookie answer with `Access-Control-Allow-Credentials: true` (`docs/api/README.md` "Browsers (CORS)"; `identity/http/client.ts:26-37` `SESSION_COOKIE_ENDPOINTS`):

- `POST /api/public/identity/app-sessions`
- `POST /api/public/identity/sessions` (sign-in)
- `POST /api/public/identity/sign-in-challenges/{id}/verify`
- `POST /api/public/identity/verifications/{id}/confirm` (registration code → signs in)
- `POST /api/public/identity/external-sign-ins` (phase 2; answers 501 `provider_not_configured` without a verifier)
- `POST /api/public/identity/sessions/refresh`
- `POST /api/public/identity/sessions/sign-out`

**Do not set `credentials: 'include'` globally.** A credentialed fetch to any other route is blocked by the browser because those responses lack `Access-Control-Allow-Credentials`. Every other call uses the default (`same-origin`) and `Authorization: Bearer`.

Preflight allows request headers `authorization, content-type, idempotency-key, x-app-proof, x-step-up-code, x-client, x-request-id, x-requested-with`; responses expose `WWW-Authenticate, X-Request-Id, Idempotent-Replayed, Retry-After` (`docs/03-auth-middleware.md` §5).

### 1.3 Start an app session (bootstrap: the only call without a token)

```http
POST /api/public/identity/app-sessions          (credentials: 'include')
Content-Type: application/json
X-App-Proof: dev                                 (prod website: turnstile:<token>; Android: play:<token>)
X-Client: web

{ "audience": "store", "device": { "kind": "web" } }
```

`201` `SessionTokens`:

```json
{ "sessionId": "<uuid = guest session id>", "audience": "store",
  "accessToken": "<jwt>", "accessTokenExpiresAt": "…",
  "refreshToken": "", "refreshTokenExpiresAt": "<now + 30 d>", "sellerId": null }
```

plus `Set-Cookie: __Secure-mk_refresh_store=v.…; Max-Age=2592000; Path=/api/public/identity/sessions; HttpOnly; Secure; SameSite=Strict`.

- Proof check: `backend/src/kernel/auth/app-proof.ts:20-41` (`dev` accepted only while `DEV_TOKENS` is on; `turnstile:` without `TURNSTILE_SECRET` → 503). Missing or failed → 401 `APP_PROOF_INVALID`.
- Rate limit `bootstrap`: 300/hour per IP, 30/hour per installation id. **Do not call it on every page load.** Boot sequence: try refresh first (1.8); only if that returns 401 (no cookie, expired), start a new app session.
- `DeviceInfo` = `{ kind: "web"|"android", name?, appVersion?, installationId? }`. The website may send a stable `installationId` (a UUID kept in localStorage): it keeps one device record per browser and is **required** for "remember this device" to skip 2-step later (`identity/service/core.ts:410-447` `deviceFor` / `trustedDevice`).
- Remember `sessionId`: it is the guest session id you pass to `POST /api/store/cart/cart/merge` after sign-in (1.9).

### 1.4 Sign in with password (and the 2-step challenge)

```http
POST /api/public/identity/sessions               (credentials: 'include')
Authorization: Bearer <visitor access token>     ← required: this is what claims the guest cart
Content-Type: application/json

{ "email": "ana@example.com", "password": "…", "audience": "store",
  "keepSignedIn": true, "device": { "kind": "web", "installationId": "…" } }
```

`200` `SignInResult` `{ status, tokens?, account?, challenge?, sellerContexts[], passwordResetToken? }`, `status` ∈ `signed_in | second_factor_required | seller_context_required | password_reset_required` (store only meets the 1st, 2nd and 4th).

- `signed_in`: `tokens` = customer `SessionTokens` (refreshToken `""`, cookie set), `account` = `AccountSummary { id, realm: "member", email, displayName, status, emailVerified, twoStepEnabled, lastActiveAt }`. Replace the visitor token with `tokens.accessToken`.
- `second_factor_required`: `challenge = { id, methods: ["totp","recovery_code"] (sms phase 2), smsPhoneMasked?, expiresAt }`. Then:

```http
POST /api/public/identity/sign-in-challenges/{challenge.id}/verify    (credentials: 'include')
Authorization: Bearer <visitor access token>

{ "method": "totp", "code": "123456", "rememberDevice": true }      → 200 SignInResult (signed_in)
```

  `rememberDevice` only works when the sign-in sent `device.installationId` (`identity/service/authentication.ts:282`). Wrong code → 400 `CODE_INVALID` (`details.attemptsLeft`); too many → 429 `CHALLENGE_LOCKED`; expired → 410 `CODE_EXPIRED`.
- `password_reset_required`: staff forced a reset; continue with `passwordResetToken` on the recover screen's set-new-password step (1.6).
- Errors: 401 `INVALID_CREDENTIALS` (`details.attemptsLeft`), 423 `ACCOUNT_LOCKED` (`details.lockedUntil`, `cause`), 403 `ACCOUNT_DISABLED`, 403 `EMAIL_NOT_VERIFIED` (`details.challenge` = fresh `VerificationChallenge`: go to the register screen's code step), 429 `RATE_LIMITED` (10/min per IP, 5 per 15 min per email).
- `body.guestSessionId` exists in the spec but the service ignores it: the claim uses the visitor token's `sid` (`identity/service/authentication.ts:105`, `core.ts:451-457`). Sign-in sent without the visitor token works but does not move the cart.
- Code: `backend/src/modules/identity/service/authentication.ts:96-178` (sign-in), `:245-290` (2-step verify).

### 1.5 Registration and email verification

```http
GET  /api/public/identity/password-policy?realm=member    → { minLength: 10, requireNumber, requireUppercase, disallowNameOrEmail, rejectBreached }

POST /api/public/identity/registrations
Authorization: Bearer <visitor access token>
{ "email": "…", "password": "…", "firstName": "Ana", "lastName": "Lee",
  "marketingOptIn": false, "acceptedTermsVersion": "<policy version shown>", "device": { "kind": "web" } }
→ 202 VerificationChallenge { id, purpose: "email_verification", emailMasked, codeLength: 6, expiresAt (+10 min), resendAvailableAt (+60 s), attemptsLeft: 5 }
```

Always 202, whether or not the email already has an account (the existing owner gets a "you already have an account" email instead of a code). Then:

```http
POST /api/public/identity/verifications/{id}/confirm       (credentials: 'include')
Authorization: Bearer <visitor access token>
{ "code": "123456", "keepSignedIn": true, "device": { "kind": "web" } }
→ 200 VerifyResult { verified: true, account, tokens }     ← signs the customer in, claims the visitor session, sets the cookie

POST /api/public/identity/verifications/{id}/resend        → 202 VerificationChallenge (429 RESEND_TOO_SOON before resendAvailableAt)
```

Errors: 400 `WEAK_PASSWORD` (`details.failed`: `min_length|number|uppercase|personal_info|breached`), 400 `CODE_INVALID`, 410 `CODE_EXPIRED`, 429 `CHALLENGE_LOCKED`. Code: `identity/service/registration.ts:50-183` (register, confirm), `:184` (resend).

**Dev gap: the code never leaves the server process.** The dev email provider records messages in an in-memory array (`backend/src/modules/notifications/providers/dev-outbox.ts`, `providers/email.ts`); no HTTP endpoint or log line exposes it, and the code is excluded from the delivery log. In development a browser registration therefore cannot be completed by hand. Options: seed customers by another route (section 2), read `devOutbox` through a debugger, or add a dev-only "last emails" endpoint to the backend (not built; needs a backend decision). The same applies to password-reset links, emailed order links and 2-step SMS.

A customer record (customers module) is created by the async `identity.user.registered` / `identity.user.verified` handlers; customer-only calls made in the same millisecond can race it.

### 1.6 Password recovery

```http
POST /api/public/identity/password-resets            { "email": "…" }  → 202 { emailMasked, expiresInMinutes: 30, resendAvailableAt }
POST /api/public/identity/password-resets/lookups    { "token": "…" }  → 200 PasswordResetStatus { valid, emailMasked?, expiresAt?, policy, forced }
POST /api/public/identity/password-resets/complete   { "token": "…", "newPassword": "…", "signOutOtherDevices": true } → 204
```

All `visitor` (Bearer visitor token), no cookie. The emailed link is **`${STORE_URL}/reset-password#token=<token>`** (`identity/service/passwords.ts:21-23`): the store app has no `/reset-password` route (its screen is `/recover`, `auth/recover`). Add a route alias that reads the fragment and shows the recover screen's new-password step. Errors: 410 `RESET_LINK_INVALID`, 400 `WEAK_PASSWORD` / `PASSWORD_REUSED`. Rate limit 5/hour per email, 20/hour per IP.

### 1.7 Guest sessions (no separate guest token)

The visitor session **is** the guest session (`docs/03-auth-middleware.md` §8). `X-Guest-Session` is retired, although some module docs (e.g. `customers.md` `GuestOrderAccess.granted`, `identity.md` Owns) still mention it: ignore it, send the visitor Bearer token. Everything `shopper` (cart, checkout, guest order pages) works with the visitor token. Guest order access:

- Checkout grants the placed order to the visitor session automatically (`grantGuestOrderAccess` via checkout), so the confirmation page and order detail work with the same visitor token.
- `POST /api/store/customers/guest-orders/lookup` `{ orderRef: "MK-YYMMDD-NNNNN", email }` → `GuestOrderAccess` (`granted: true` adds the order to the caller's visitor session; then read `GET /api/store/orders/orders/{id}` with the same token).
- `POST /api/store/customers/guest-orders/links` `{ email }` → 202 (emails fresh order links).
- Emailed order link `${STORE_URL}/orders/open#token=<token>` (`identity/service/guests.ts:53`) → `POST /api/public/identity/order-links/redeem { token }` → `OrderLinkRedemption { guestSession, orderId, emailMasked }`. The store app has no `/orders/open` route: add one.
- Grants last `guestOrderAccessDays` (90); links `orderLinkTtlDays` (180).

### 1.8 Refresh

```http
POST /api/public/identity/sessions/refresh       (credentials: 'include')
Content-Type: application/json
X-Requested-With: XMLHttpRequest                 (any value; required with the cookie)
(Origin is sent by the browser; must be in any app's CORS_*_ORIGINS or equal API_URL's origin)

{ "audience": "store" }
→ 200 SessionTokens (new accessToken, refreshToken "", new cookie)
```

- No `Authorization` header needed (auth kind `refresh`, verified from the cookie in middleware: `kernel/auth/chain.ts:100-107`, guard `chain.ts:436-444`).
- Without `audience` no cookie is read → 401 `token_missing`. Without `X-Requested-With` → 403 `FORBIDDEN` `x_requested_with_required`; bad Origin → 403 `origin_not_allowed`.
- Refused token: 401 `UNAUTHORIZED` `token_invalid` / `REFRESH_TOKEN_INVALID`, 403 `ACCOUNT_DISABLED`, 423 `ACCOUNT_LOCKED` → customers sign in again; visitors start a new app session.
- Works for visitor sessions too (same endpoint, same cookie).
- 30 refreshes/hour per session. The previous token sent again within 20 s returns the same new pair (two tabs); later it **ends the session**. Serialize refreshes (one in-flight promise shared by all callers; a `BroadcastChannel` or Web Lock across tabs).
- When to refresh: only on 401 `UNAUTHORIZED` with `details.reason` starting `token_` (`token_expired`, `token_revoked`, …). Never on `session_idle`, `sign_in_required`, 403s, or a GraphQL field `FORBIDDEN` inside a 200. Retry the original request once.

### 1.9 Sign-out

```http
POST /api/public/identity/sessions/sign-out      (credentials: 'include', X-Requested-With: 1)
{ "audience": "store" }
→ 204, Set-Cookie: __Secure-mk_refresh_store=; Max-Age=0; …
```

Clears only the store cookie. Signing out with an unknown or already-ended token is 401. After sign-out start a fresh app session (new empty guest cart). Other session management (`account` auth, any signed-in token): `GET /api/store/identity/devices`, `POST /api/store/identity/devices/{id}/sign-out`, `POST /api/store/identity/devices/sign-out-all { keepThisDevice }`.

### 1.10 How sign-in claims the visitor's cart

1. Sign-in / 2-step verify / registration confirm runs with the visitor Bearer token → identity marks that guest session claimed and expires it (`identity/service/core.ts:451-457`), then publishes `identity.guest_session.claimed { guestSessionId, accountId }` (store sessions only; `core.ts:519-533`).
2. Subscribers (in-process, **asynchronous**: `backend/src/kernel/events/index.ts:76-95`, delivered on the next tick, lost if the process dies): cart merges the guest cart into the customer cart (`modules/cart/service.ts:1033`), checkout attaches open guest checkout sessions (`modules/checkout/service.ts:588`), customers merges recently viewed (`modules/customers/service/recently-viewed.ts:131`).
3. To show the one-time message ("We added 2 items from before you signed in"), call `POST /api/store/cart/cart/merge { guestSessionId: <visitor sessionId> }` with the customer token → `MergeResult { cart: CartView, report: { mergedFromCartId, lines[{ title, outcome: added|quantity_combined|capped_at_limit|kept_separate_offer|dropped_unavailable, note }], savedItemsMoved, message } }`. It is idempotent (an already merged cart answers its stored report) but answers 404 until the claim event has been recorded (`cart/service.ts:554-563`): on 404, re-read `GET /api/store/cart/cart` after a short delay.
4. The visitor token is dead after the claim; never fall back to it. After sign-out, bootstrap a new visitor session.

### 1.11 Step-up on store screens

- `reauth` kind (body `reauthToken`): get it with `POST /api/store/identity/reauth { purpose, password? | code? }` → `{ reauthToken, expiresAt (+5 min) }`; single use, bound to `purpose` ∈ `account-closure | email-change | two-step-removal | recovery-codes` for the store. Used by `POST /api/store/identity/email-changes`, `/two-step/methods/{id}/remove`, `/two-step/recovery-codes`, `POST /api/store/customers/data-requests/closure`.
- Missing / refused proof → 403 `STEP_UP_REQUIRED { kind, purpose }` (never 400). With a dev-key customer token, `reauthToken: "dev-reauth.<purpose>"` and code `000000` are accepted.


## 2. Dev tokens and seeding

> **2026-10-17:** the web seed (`web-shared/tools/seed`) has been removed. The apps are wired to the backend, and sample data comes from the backend's own simulator (`npm run simulate` in the backend). This section is kept as history.

**Bottom line.** No seed tool exists in `Ecommerce-api`. `backend/src/testing/flows.ts` is the reference for the real setup sequences, but it is **not HTTP-only**: it runs in-process (`app.inject`, fake clock), drains events after every call (`flows.ts:102-108`), reads invitation links and email codes from in-process events (`:99-101,130,194`), reads the seller invitation code from the service (`:222-223`), runs `media.process` directly (`:212`) and publishes `finance.destination.verified` itself (`:377`, with a stale "finance is not built" comment). Items marked **[unverified]** were not traced in code.

### 2.1 Server settings for a seed run

| Setting | Why |
|---|---|
| `MONGO_DATA_DIR=.data/mongo` (local `.env` already has it) or a local `MONGODB_URI` | Without either, `npm run dev` uses an in-memory replica set: everything is lost on restart. `bootstrap-owner` refuses the in-memory DB. |
| **`JOBS_ENABLED=true`** (local `.env`: `false`) | Nothing scheduled runs otherwise, and no HTTP endpoint runs a job: `media.process` (images stay `processing`; attaching waits ~10 s then fails, `media/service.ts:1413-1427`), **`search.process-dirty`** (every 30 s; offers created after product approval never reach search, `search/service/indexer.ts:216-251`), `notifications.dispatch`, `payments.process-refunds`, `payments.check-uncertain`, `promotions.start-due`/`end-due`, `content.run-schedules`, `content.policy-effective`, `content.cache-warm` (homepage cache, 5 min), `inventory.expire-holds`, `orders.complete-orders`, `reviews.summaries` (10 min). |
| `RATE_LIMITS=false` (allowed outside production, `config/index.ts:183,209`) | A seed hits 600/min per IP, 30 writes/min per customer, sign-in 5 per 15 min per email, registration 20/h per IP, bootstrap 300/h per IP. |
| `DEV_TOKENS` on (default) | Dev tokens, `X-App-Proof: dev`, step-up `000000`, `dev-reauth.<purpose>`, webhook secret `dev-webhook-secret`, fixed `APP_SECRET=dev-app-secret-not-for-production-use-0000` (`config/index.ts:172,180,188`). Requires loopback `HOST` and local MongoDB. |
| Same `DEV_SIGNING_KEY_FILE` for server and seed | Default `.data/dev-signing-key.json` relative to the working directory (`backend/`). |

The dev card processor, `devOutbox` and in-memory rate limits are per process: finish each order's payment/refund life within one server run.

### 2.2 `backend/tools/token.ts`

```
cd backend
npm run -s token -- visitor  [--audience store|seller|admin]                          # default store
npm run -s token -- customer [--account <uuid>]
npm run -s token -- seller   [--seller <uuid>] [--account <uuid>] [--permissions a,b]   # owner unless --permissions
npm run -s token -- staff    [--account <uuid>] [--permissions k1,k2]                   # default ['*']
```

- Flags parsed at `tools/token.ts:16-19`; no `--customer`, no `--ttl` (fixed **12 h**, `:32-33`). Prints the bare JWT. Exits 1 if `DEV_TOKENS` is off (`:26-29`). **Needs neither the DB nor the server**: it loads config and the key file (creating it on first use, `kernel/auth/tokens.ts:180-195`). A seed in another repo can shell out to it (`cwd: E:/Work/Ecommerce-api/backend`).
- Claims (`backend/src/kernel/auth/dev.ts:21-36`), all with a fresh random `sid`:

| Kind | Claims |
|---|---|
| visitor | `{ aud: store (or --audience), kind: "visitor", sid, dev: {} }` |
| customer | `{ aud: "store", kind, sub: --account \| random, sid, authAt, dev: {} }` |
| seller | `{ aud: "seller", kind, sub, sid, authAt, sellerId: --seller \| random, memberId: sub, dev: { isOwner: !permissions, permissions } }` |
| staff | `{ aud: "admin", kind, sub, sid, authAt, twoStepAt: now, dev: { permissions: ["*"] \| list } }` |

- **Minting without the CLI** (as `backend/tools/test-http.ts` does): read the Ed25519 private JWK `{kty:"OKP",crv:"Ed25519",x,d}` from the key file; `kid = "dev-" + sha256(SPKI DER of the public key).hex.slice(0,12)` (`tokens.ts:193`); header `{alg:"EdDSA", typ:"at+jwt", kid}`; claims above plus `iss: "marketly-identity"`, `iat`, `exp`. The verifier checks alg, typ, known kid, `iss`, `aud`, `kind`, `sid`, `sub` (non-visitors), `exp`/`iat` with 60 s leeway; `jti` is not checked; `dev` claims are honoured only on `dev-` kids (`tokens.ts:133-157`). Optional `dev.name` becomes the actor name in audit (`auth/index.ts:170`).
- Revocation is only an in-memory list polled from identity (`revocation.ts:305-309`): a random `sid` is never revoked; dev staff tokens skip the staff-session liveness/idle check (`chain.ts:256-257`).

**What dev tokens bypass and what they don't** (`backend/src/kernel/auth/authorities.ts:83-109`):

| | Dev token |
|---|---|
| Staff permissions | `dev.permissions` (`*` = all) instead of access roles |
| Staff 2-step sign-in | covered by `twoStepAt` (no TOTP) |
| Step-up `code` | `X-Step-Up-Code: 000000` |
| Step-up `reauth` | `reauthToken: "dev-reauth.<purpose>"` |
| Seller membership | taken from the token (no member row); owner unless `--permissions` |
| **Approval limits / maker-checker** | **not bypassed.** `access.check()` resolves roles by `principal.accountId`; a random `sub` has no roles → `denied` (403) on limited actions (`modules/access/service/approvals.ts:94-110`). The requester can never decide their own request (`SELF_APPROVAL_NOT_ALLOWED`, `:302-306`). **Fix:** mint with `--account <real Business Owner accountId>`; the Business Owner role is unlimited (`access/domain/seed.ts:49`). Two different BO accounts cover two-person rules. |
| **Real records** | A seller token needs a real approved seller (`--seller <id> --account <owner accountId>`): modules load the seller by `sellerId`. A customer token needs a real identity member account: the customer profile is created only for one (`customers/service/profiles.ts:29-52`); a random `sub` gives 404 "Customer profile" / "Customer not found" at checkout. |

Limited actions met while seeding (`access/domain/seed.ts`): `inventory.adjustments.apply` (Inventory Manager ≤ 50 units), `offers.prices.change`, `promotions.budgets.approve`, `content.policies.approve` (recommend-only for Content Manager → Business Owner decides), `returns.refunds.approve`, `settings.changes.apply`, `purchasing.orders.send`, finance actions, seller restrict/suspend.

## 3. Screen → API map (all 59 store screens)

Per screen: route, what the page shows (from the page and its sample data), the persisted GraphQL screen query if one fits (`docs/api/graphql/operations/store/*.graphql`, ids in `manifest.json`), REST reads, REST writes for the page's actions, auth kind, gaps. `x-screens` in `openapi.json` already lists the endpoints the design intended for each screen; the tables below are checked against the module docs. Paths are full unless abbreviated in the area's note.

**Read before the tables:**

1. **Persisted queries at launch.** Usable: `OffersPage`, `CartPage`, `CheckoutReview`, `OrderConfirmation`, `OrderList`, `OrderDetail`, `ReturnDetail`, `CaseDetail`. **Fail validation** in the launch module set (`backend/src/app.test.ts:88-89`): `HomePage`, `CategoryPage`, `SearchResults` (also search-empty), `ProductPage`, `SellerStorefront` (all select `Product.saved`, wishlist) and `AccountOverview` (`Customer.wallet`). Until the backend fixes them, those screens use REST (production) or the trimmed query text (dev only, §4.4).
2. **Product routes can't be resolved from a slug.** Every product endpoint takes the uuid (`GET /api/store/catalog/products/{id}`, `/api/store/offers/products/{productId}/…`, `/api/store/reviews/products/{productId}/…`; GraphQL `product(id: UUID!)`, `schema.store.graphql:605`) and no slug lookup exists. Categories (`/catalog/categories/{slug}`), brands (`/catalog/brands/{slug}`), stores (`/sellers/stores/{slug}`) and content pages (`/content/pages/{slug}`) **do** resolve by slug. Fix in the app (`/p/:slug/:id` or `/p/:id`) or ask for a lookup endpoint.
3. **Account/help routes carry refs (`MK-…`, `RT-…`, `CS-…`), REST takes uuids.** Resolve with GraphQL `order(ref)` / `return(ref)` / `case(ref)` (§3.4).
4. **Cards.** `search.ProductCard` (from `/search/products`, `/search/cards?ids=`, `/similar`) is the only complete card: `slug, title, image, price, wasPrice, discountPct, priceIsFrom, offerCount, rating, ratingCount, sellerName, official, deliveryCue, freeDelivery, availability, badges`. `content.ProductTile`, `promotions.DealProduct`/`FlashItem`, content category/seller/brand tiles and storefront categories lack slugs and/or delivery cue and offer count: fill them with `GET /api/store/search/cards?ids=…`.
5. **Phase 3.** Wishlist and wallet modules are off: their routes don't exist (**404 `NOT_FOUND` "No route"**), and `GET /api/public/settings/app-config` reports `features.wishlist=false`: hide every heart, "notify me", store-credit UI. Phase-3 endpoints of enabled modules (cart save-for-later, checkout credit, push prefs) answer **501 `later_phase`**.
6. **Ads** are always REST: `POST /api/store/advertising/decisions` (shopper; `ServeRequest{ page: home|category|search|product|campaign|collection|deals|brand|seller_store|official_store, context, device, visitorId, sessionId, isEntryPage, slots, personalizationAllowed }` → `ServeDecision{ overlay, slots, sponsoredProducts[], ttlSeconds }`), then `POST /api/store/advertising/events { events: [TrackEvent] }` with the impression token. Sponsored search hits come inline from `/search/products` page 1.
7. **Header/layout on every store page:** `GET /api/store/cart/cart/badge` (shopper), `GET /api/store/messaging/unread-count` (shopper), `GET /api/store/notifications/inbox/summary` (customer), `GET /api/store/content/navigation` (visitor), `GET /api/public/settings/app-config` (visitor: features, support, maintenance), `GET /api/store/search/suggestions?q` (visitor), `GET /api/store/search/recent-searches` (shopper).

## 4. Client conventions to follow

### 4.1 Request headers (every call)

| Header | Rule |
|---|---|
| `Authorization: Bearer <token>` | Every request, GraphQL included: visitor token before sign-in, customer token after. No token → 401 even for URLs that don't exist (401 before 404). |
| `X-Client: web` | Analytics and the Android minimum-version gate only (`kernel/auth/chain.ts` `#checkClientVersion`); never trusted for auth. |
| `X-Request-Id` | Optional; 1–100 of `[A-Za-z0-9_-]`, else the server makes one. Every response carries it: log/show it on failures. |
| `Idempotency-Key` | Required on idempotent endpoints (missing → 400 `VALIDATION_FAILED`). Store endpoints that need it: `POST /api/store/checkout/sessions/{id}/place`, `…/{id}/complete-action`, `…/{id}/retry-payment`, `POST /api/store/orders/orders/{id}/cancellations`, `POST /api/store/payments/refunds/{id}/destination`, `POST /api/store/returns/requests`, `POST /api/store/support/cases` (+ phase 3 `POST /api/store/wallet/gift-cards/redeem`). One key (UUID) per user action, reused on every retry of that action; kept 24 h per operation and caller. Same key + same request → first response again with `Idempotent-Replayed: true`; same key + different path/query/body → 422 `IDEMPOTENCY_KEY_REUSED`; still running → 409 `CONFLICT`; handler failure frees the key. |
| `X-Step-Up-Code` | Only for `stepUp: code` endpoints (staff-side; none on store screens). Store step-ups use `reauthToken` in the body (§1.11). |
| `X-Requested-With` | Only on refresh and sign-out (cookie). |
| `X-App-Proof` | Only on `POST /api/public/identity/app-sessions` (`dev` in development). |
| `Accept-Language` | Ignored; all text is en-US. |

Trailing slashes are ignored. Every `/api`, `/graphql`, `/webhooks` response is `Cache-Control: private, no-store` (no CDN/HTTP caching; cache in TanStack Query instead).

### 4.2 Errors

REST: `{ "error": { "code", "message", "details"? } }` (`docs/api/README.md` "Errors"; `backend/src/spec/common.ts` `ErrorBody`). Switch on `code`, never on `message`.

| Code | Status | Client action |
|---|---|---|
| `VALIDATION_FAILED` | 400 | `details.issues[{ path: "body.email", message }]` → field errors. Also 400/413/415 with no details for unreadable JSON, >2 MB body, wrong content type. |
| `UNAUTHORIZED` | 401 | `details.reason` `token_*` → refresh once, retry once. `sign_in_required` → send to sign-in (a visitor called a `customer` endpoint). `session_idle` → sign in again. |
| `FORBIDDEN` | 403 | `details.permission` or `details.reason`. |
| `WRONG_AUDIENCE` | 403 | Token of another app (seller/admin token on the store). |
| `STEP_UP_REQUIRED` | 403 | `details.kind` (`reauth` / `code`), `details.purpose` → ask for password/code, call `/api/store/identity/reauth`, retry with `reauthToken`. |
| `NOT_FOUND` | 404 | Also "not yours" (another customer's order) and routes of modules that are off (wishlist, wallet: `No route …`). |
| `ILLEGAL_TRANSITION` | 409 | `details.machine, from, event, allowed` (e.g. cancel an already shipped item). Reload. |
| `CONFLICT` | 409 | Concurrent change / idempotent request still running. Reload, retry. |
| `APPROVAL_REQUIRED` | 409 | Staff-side; not expected on store screens. |
| `IDEMPOTENCY_KEY_REUSED` | 422 | Bug: new action reused an old key. |
| `ACCOUNT_LOCKED` | 423 | `details.lockedUntil`. |
| `UPGRADE_REQUIRED` | 426 | Android only. |
| `RATE_LIMITED` | 429 | Wait `Retry-After` seconds (`details.retryAfterSeconds`). |
| `NOT_IMPLEMENTED` | 501 | `details.reason`: `later_phase` (endpoint of a phase above `LAUNCH_PHASE=2`, e.g. cart save-for-later, checkout store credit), `not_built`, `provider_not_configured`. Hide the feature. |
| `SERVICE_UNAVAILABLE` | 503 | Retry with backoff. |
| `INTERNAL_ERROR` | 500 | Show the `X-Request-Id`. In dev, `RESPONSE_VALIDATION` is on: a response that doesn't match the spec is a 500 too. |

Module codes (e.g. `OFFER_CHANGED`, `INVALID_CREDENTIALS`, `CODE_INVALID`, `EMAIL_NOT_VERIFIED`, cart/checkout/promotion codes) are listed per module in `docs/api/modules/<module>.md` → "Error codes".

GraphQL: `{ data, errors[] }` with `errors[].extensions.code` (+ `extensions.details`), HTTP 200 whenever some data came back. A field the caller may not read answers `FORBIDDEN` inside a 200 (`details.reason: sign_in_required` for a guest asking a customer field): **never refresh on it**. Own codes: `QUERY_TOO_COMPLEX`, `QUERY_TIMEOUT`, `PERSISTED_QUERY_NOT_FOUND`, `PERSISTED_QUERY_NOT_SUPPORTED` (`docs/api/graphql/README.md` "Errors").

### 4.3 Paging

REST list endpoints take **either** `cursor` (Android infinite scroll) **or** `page` (website numbered pages, 1-based), never both, plus `limit` 1–100 (default 24). Response `{ items, nextCursor, page?, totalPages?, total? }`; `nextCursor` is null at the end. Both params, out-of-range limit, or an unreadable cursor → 400. The website's `<Pager>` (numbers on desktop, lazy-load row on phone) maps to `page` on desktop and `cursor` on phone. GraphQL takes `paging: { cursor | page, limit }` (`PageInput`) and clamps the limit instead of refusing (`backend/src/spec/common.ts:12-41`; `docs/api/graphql/base.graphql` `PageInput`).

### 4.4 GraphQL request format

- Endpoint `POST /graphql/store` (also `GET` with `query`/`variables`/`extensions` as JSON in the query string). Same Bearer token; auth kind `visitor` (visitor or customer). Read-only: no mutations, no subscriptions; all writes are REST.
- Persisted (production): `{ "persisted": true, "query": "<sha256 id>", "variables": {…} }` or Apollo APQ `{ "extensions": { "persistedQuery": { "version": 1, "sha256Hash": "<id>" } }, "variables": {…} }`. Ids: `docs/api/graphql/operations/store/manifest.json`.
- Development (`GRAPHQL_PERSISTED_ONLY=false`): plain `{ "query": "query HomePage(…) {…}", "variables": {…} }` also runs. In production free text → 400 `PERSISTED_QUERY_NOT_SUPPORTED`.
- **Launch-config breakage:** `HomePage`, `ProductPage`, `CategoryPage`, `SearchResults`, `SellerStorefront` and `AccountOverview` select `Product.saved` (wishlist) and `AccountOverview` selects `Customer.wallet` (wallet); both modules are off (`backend/src/modules.config.ts:47-49`). The persisted ids of those 6 store queries therefore fail validation (the server only warns at startup: `backend/src/kernel/graphql/index.ts:355-361` `unusablePersistedQueries`; asserted in `backend/src/app.test.ts:88-89`; `backend/README.md` "Open points in the design"). `CartPage.savedForLater` (cart, phase 3) is not in that list and just stays empty. Until the backend fixes the operations, send the operation text **without** `saved` / `wallet` as free text (dev only), and ask the backend to regenerate the manifests (or to keep `@phase` fields resolving to null) before production.
- Limits: depth 9, cost 1,500, page size clamped 1–100, 10 s per request.
- Recommended client (backend design): GraphQL Code Generator types from `docs/api/graphql/schema.store.graphql` + TanStack Query.

### 4.5 Money, dates, ids

| Kind | Format |
|---|---|
| Money (REST) | `{ amount: int, currency: "USD" }`, **integer minor units (cents)**: `18900` = $189.00 (`backend/src/spec/common.ts:44-54`). The web formatter `money(n)` (`web-shared/src/lib/format.ts`) takes **dollars**: call `money(m.amount / 100)` or add a `moneyOf(m)` helper. |
| Money (GraphQL) | `Money { amount: Int! (cents), currency: String!, formatted: String! ("$189.00") }` (`docs/api/graphql/base.graphql:87-93`): prefer `formatted` for display. |
| Ids | UUIDv7 strings everywhere (`scalar UUID "UUIDv7 string"`). |
| Human refs | Order `MK-YYMMDD-NNNNN` (market time zone, prefix setting `orderRefPrefix`), return `RT-YYMMDD-NNNN`, case `CS-YYMMDD-NNNN`, refund `RF-YYMMDD-NNNN`, seller appeal `SAP-…`, catalog submission `SUB-…`, approvals `AP-…`. **Every REST path parameter is a uuid; no store REST endpoint looks up by ref.** Resolve refs with GraphQL `order(ref)`, `return(ref)`, `case(ref)` (return `id`) or `GET /api/store/orders/orders?q=<ref>`. |
| Slugs | Categories, brands, seller stores, content pages and help articles resolve by slug; **products only by uuid** (no slug lookup in REST or GraphQL). |
| Dates | `DateTime` ISO 8601 UTC; `Date` `YYYY-MM-DD`. Market time zone `America/Los_Angeles`, currency `USD`, default delivery location `97205` / "Portland" until the shopper sets one (`MARKET_DEFAULT_POSTAL_CODE`, `MARKET_DEFAULT_LOCATION_LABEL`). |
| Address | `{ name, line1, line2?, city, region ("OR"), postalCode, country ("US"), phone? }`. |
| Media | `MediaRef { id, url, alt?, width?, height?, bytes? }`; `url` is a signed file link `GET /files/{bucket}/{key}?…` (public renditions permanent, private files 10 min). `<img src>` works without a token. |
| Actor | `{ kind: customer|visitor|seller|staff|provider|anonymous|system, id?, name? }`. |

### 4.6 Official Store

`OFFICIAL_STORE_ID = "00000000-0000-7000-8000-000000000001"`, `OFFICIAL_STORE_NAME = "Marketly Official Store"` (`docs/api/README.md` "Constants"; `backend/src/spec/common.ts`). It is the seller id of first-party offers wherever a seller id appears (cart packages, orders, reviews/feedback, returns terms, conversations). The sellers module never issues it, so `GET /api/store/sellers/stores/{slug}` has no Official Store record: the `store/official` screen reads it through search/reviews with `sellerId = OFFICIAL_STORE_ID` (section 3). Put both constants in `web-shared/src/config.ts` and never hard-code the label.

### 4.7 Uploads (reviews, returns, cases, messages, seller application)

`POST /api/store/media/uploads { purpose, fileName, contentType, sizeBytes, sha256? }` → `UploadTicket{ uploadId, assetId, method, url, headers, maxBytes, expiresAt }` → `PUT` the bytes to `url` with the returned `headers` (+ Bearer; dev storage is the API's own `/api/store/media/uploads/{id}/content`) → `POST /api/store/media/uploads/{id}/complete` (202) → poll `GET /api/store/media/assets/{id}` until `status: "ready"` (processing is the `media.process` job) → pass `assetId`s as `mediaIds`. Purposes: `return_evidence` (15 MB; jpeg/png/webp/heic/mp4), `review_photo`, `case_evidence`, `message_attachment`, `verification_document`. `MediaRef.fileName` is the uploaded file name (G31d; `mediaFileName()` in web-shared/src/api/uploads.ts).

### 4.8 Suggested client module (`web-shared/src/api/`; an uncommitted implementation already exists there: check it against this list)

1. `session.ts`: in-memory access token, boot (refresh → else app-session), single-flight refresh, sign-in/registration/sign-out, `onAuthChange`.
2. `http.ts`: `api<T>(method, path, { body, query, idempotencyKey, credentials })` adding `Authorization`, `X-Client: web`, `X-Request-Id`; parses the error envelope into a typed `ApiError { status, code, details, requestId }`; refreshes once on `401 token_*`.
3. `graphql.ts`: `gql<T>(name, variables)` sending persisted ids in production and the trimmed operation text in development.
4. Generated types: `openapi-typescript` from `docs/api/openapi.json`, GraphQL codegen from `schema.store.graphql`.


## 5. Recommended tranche-1 order

Goal: a working **browse → product → cart → checkout → order → account** path on real data, guest and signed-in. Use REST for every screen whose persisted query fails at launch; GraphQL only where the query works (`CartPage`, `CheckoutReview`, `OrderConfirmation`, `OrderList`, `OrderDetail`).

### 5.0 Decisions to take first (they change routes or the backend)
